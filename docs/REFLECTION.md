# CodeCoach AI Reflection

Building CodeCoach AI changed from a straightforward frontend exercise into a practical lesson in production boundaries. The first version worked locally because Vite proxied relative `/api/*` requests to an Express process running on my machine. That assumption disappeared in Vercel. The frontend deployed successfully, but the Express process was not automatically exposed as production API routes. The fix was to keep one shared Express application and expose it through Vercel functions for health, hints, explanations, and deterministic runs.

The most useful debugging moment came from comparing the two AI features instead of changing their UI messages. Explain Code and Get Hint shared the same validation, Gemini client, model, JSON mode, and Zod boundary, so the behavior needed evidence. Safe server diagnostics showed two separate provider problems. Explain could succeed with the same implementation locally, but quota exhaustion produced HTTP 429 in production. Hint also encountered truncated JSON before the quota was exhausted, which made the friendly frontend message look like a generic application failure. The service now classifies rate limits, timeouts, provider failures, and malformed structured output. The API returns HTTP 429 for quota pressure, while logs record only a safe endpoint, error category, status, and redacted provider message.

I also learned that structured output is a contract, not a guarantee. A response schema must be validated after the SDK returns, and the output budget must leave enough room for every required field. Hint and Explain now use separate bounded budgets and stricter schemas. Tests cover successful responses, repeated hints, rate limits, malformed explanation data, invalid requests, unknown challenges, and the deterministic evaluator. The evaluator remains separate from Gemini, which keeps completion decisions reproducible.

The remaining operational lesson is that a passing local build is not proof of a healthy deployment. Vercel environment variables, function discovery, provider quota, production health checks, and Lighthouse evidence all need explicit verification. The project now documents those checks and keeps the API key server-side. The next improvement would be adding a small persistent learning history and a provider health dashboard, while keeping quota behavior visible and honest to the learner.
